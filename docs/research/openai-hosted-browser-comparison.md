Status: offline public-probe request builder, 2026-10-04. No hosted-browser session or employer request has been started from this branch. Candidate-bearing hosted submission remains blocked; this builder is not a submission guard.

RoleDawn's form agent already uses the Agents API with `environment.type: "none"` and function tools. The employer browser is a separately controlled Browserbase/Playwright runtime. Changing the model alone would not compare browser providers. The [Agents API computer-use guide](https://developers.openai.com/api/docs/guides/agents-api/tools/computer-use) describes a different runtime: a `computer_use` tool in an `openai_hosted` environment with desktop enabled. Its session event stream must be open before posting the task; each new website origin produces a `computer_use_approval_request` that requires a decision through the session events API.

The guide explicitly says origin approval does not enforce confirmation before each consequential browser action. RoleDawn's sealed, single-use submit permission is enforced by its controlled browser runtime. Direct candidate submission through the built-in hosted browser would bypass that enforcement. A noncandidate public-page probe avoids sharing applicant data, but a prompt alone does not block an HTTP POST. A candidate submission path needs a server-enforced equivalent before it can be used for acceptance.

For a bounded public-page comparison, configure the hosted sandbox with [restricted network access](https://developers.openai.com/api/docs/guides/agents-api/environments/openai-hosted) to exact required host names where feasible. Browser origin approval is a separate decision. Record only redacted lifecycle markers, requested origins, session and turn IDs, and usage. Delete the session after the task; a closed event stream alone does not stop it. [Agent usage](https://developers.openai.com/api/docs/guides/agents-api/observability) is best effort and is not an invoice. [Container time and model tokens](https://developers.openai.com/api/docs/pricing) both count toward a comparison budget.

An organization costs read requires an appropriately authorized billing credential. A failed billing read does not by itself prove a budget was reached. Project browser-minute metering, an unknown invoice, and unretained prior model-token totals cannot establish a numeric upper bound on aggregate dollars. A conservative future probe estimate needs: a confirmed prior billed amount or credible upper bound; its chosen model/service tier and context length; a total input/output token allowance across all model calls; container size and elapsed billable minutes; and any other tools. The [current pricing table](https://developers.openai.com/api/docs/pricing) lists 4 GB containers at $0.12 per 20-minute session with eligible minute billing and a five-minute minimum, and multiple GPT-6 Astra rates by tier/context. Use the rate for the actual tier or a higher published rate; do not infer an invoice from best-effort session usage. A noncandidate public-page probe cannot count toward the employer-confirmed nine-job release gate.

An opt-in request builder in `src/server/workers/openai-hosted-browser-probe.ts` is restricted to public Lever or Ashby job URLs, exact network host names, no candidate packet, no caller-supplied prompt or files, and an explicit origin decision. It has no path to the submit authority or receipt writer. It is not wired into production or run live. These constraints preserve RoleDawn's single-use submission invariant because any candidate send still uses the controlled runtime. They do not make the built-in hosted browser safe for a candidate-bearing employer form: the API documents no mandatory per-click or per-request interception hook for this tool. A custom browser runtime with application-enforced network and action checks is the documented way to guarantee that invariant; that would be a different browser comparison from the built-in OpenAI-hosted desktop.

## Submission architecture decision

**2026-10-04 design review:** the following controls are useful but insufficient for the built-in hosted desktop:

| Proposed control | What it enforces | Remaining failure |
| --- | --- | --- |
| One application lease and immutable packet | One worker owns the approved candidate/job/packet version | The browser can issue multiple employer requests during that worker's turn. |
| One task or one active turn | Restricts application orchestration | One turn can include many tool calls; a message during work steers the active turn. |
| Function-tool submit permission | The function can validate the existing sealed permission | Built-in computer use need not call the function before clicking or sending. |
| Stop/delete immediately after submission | Bounds later work after the signal is received | First and duplicate requests can already be in flight. Cancellation is not transactional rollback. |
| Restricted exact employer host | Limits outbound destinations | Upload, draft, submit and duplicate submit can share one allowed host. |
| Published traces and receipts | Supports diagnosis and reconciliation | Traces arrive after work and cannot prevent a request. Model text is not a receipt. |

**Concrete supported alternative, not implemented as a new provider:** retain the Agents API function-tool agent with `environment.type: none` and an application-controlled browser runtime. A provider adapter may supply a Playwright/CDP browser only if it supports the existing mandatory request guard, service-worker handling, verified upload bytes, exact destination/payload/field readback, and final durable authority callback. The agent receives no raw CDP, shell, unguarded navigation or fetch tool. Preserve the existing database lease and packet/version bindings; consume the existing one-use submit authority immediately before the matching employer request leaves the controlled runtime; block additional new submissions under that authority while preserving the existing bounded protocol exceptions; classify an ambiguous network outcome as uncertain and reconcile before retry. Reuse the current protocol predicates and receipt writer rather than introducing a second ledger or in-memory substitute for durable authority. A successful outcome here would be an alternative runtime test, **not** built-in OpenAI-hosted browser acceptance.

The currently available Browserbase adapter already provides that controlled-runtime boundary. It remains the approved fallback for previously named Lever applications after credentials, current readback, spend verification and duplicate checks. There is no reason to remove its fixes while investigating another provider. The supported integration pattern is described in [computer-use integration recipes](https://developers.openai.com/api/docs/guides/tools-computer-use-integration); it does not document an interception hook for the built-in Agents API desktop.

## Redacted trace inspection

`src/server/workers/openai-hosted-browser-traces.ts` and `scripts/read-hosted-browser-traces.ts` read **existing** sessions via the documented [session traces endpoint](https://developers.openai.com/api/reference/resources/beta/subresources/agents/subresources/sessions/subresources/traces/methods/list). They never create a session, send a task, or write application state. The endpoint's trace `id` is the root turn ID, allowing correlation with a private operator-owned turn/stage map. Use a single stage only when that turn belongs to that stage; leave mixed or unknown turns unmapped.

The reader bounds requests to five pages, one trace per page, 2 MiB per response and a 15-second transport timeout. It rejects session mismatches and repeated pagination, hashes session/turn identifiers, and exports only stage, span count, failed-span count and unset-status count. Names, attributes, prompts, tool inputs/outputs, screenshots, URL paths, error messages, and purported hidden reasoning are discarded. Permission failures remain a fixed diagnostic. This is offline-tested diagnostic tooling, not a live collector wired into production.

Run only with an authorized existing session and a private manifest outside the repository:

```bash
node --use-env-proxy --experimental-strip-types --env-file=.env.local scripts/read-hosted-browser-traces.ts /absolute/private/manifest.json
```

The manifest shape is `{ "sessionId": "sess_example", "stages": { "turn_example": "INSPECTION" } }`. Allowed stages are SETUP, INSPECTION, FILL, READBACK, VERIFICATION, SUBMISSION and RECONCILIATION. Trace export must be enabled for the organization and the project key needs `api.traces.read` or `api.agents.read`. Empty/pending traces do not prove zero work or zero cost; pagination completion does not mean late traces or billing are complete.

For tool/network/verification/receipt investigation, correlate this turn summary with the existing controlled-runtime worker events and authoritative employer evidence. The built-in trace API is not documented as a complete browser network log. Do not infer a CAPTCHA token, employer POST, or receipt from span completion. No live trace access or network/receipt observability for the native desktop has been verified.

## Review boundary: one task versus one employer request

**Required review, not authorization to change production:** the current invariant is pre-dispatch validation of the exact job, payload and readback, followed by one new submission per sealed authority, with existing bounded protocol exceptions. It is not a blanket ban on every later POST: Greenhouse verification can resend the same sealed body with its verification code, and authoritative NOT_ACCEPTED outcomes have their own retry rules. Those flows remain untouched. A built-in hosted session cannot inherit these controls merely by storing a submit permission in the application database.

A concrete counterexample is one worker holding one lease, starting one task with one immutable packet, while that task double-clicks Submit or executes a second submit after a delayed response. Both requests can leave the same approved origin before the controller receives a completion event. There is still only one lease and one task. Cancelling the session after the first observed response cannot undo the second request. This is a design counterexample, not an observed employer event.

Two review choices are distinct:

1. **Keep the current guarantee.** Do not provide applicant data to native hosted computer use. Require a documented mandatory interception boundary or use the separately controlled runtime described above. No approval-policy or ledger weakening is needed. A native public-page probe remains diagnostic only.
2. **Consider a narrowly scoped experiment with a weaker guarantee.** Explicitly review and approve the change from enforced exact-job/payload/readback validation and one new submission per sealed authority to at-most-one task dispatch for an intended application/packet/destination. This loses mandatory exact-job/payload enforcement as well as duplicate-request prevention within the task: shared ATS hosts can expose other jobs and mutable form values. An ordinary origin approval or general request to try hosted browsing is not that approval. A single scoped experimental approval has since been recorded privately; it does not authorize general delivery or remove the prerequisites below.

If the second choice is ever approved, the minimum design must retain a durable one-shot task dispatch reservation, an immutable candidate/job/packet binding, a unique destination-scoped run, and a conservative ambiguity boundary. Commit the dispatch reservation before contacting the provider. If creation or task submission times out, do not automatically create a replacement session or send a replacement task. Recover the original session by its retained identity where possible; otherwise mark the run uncertain for authoritative reconciliation. A lease expiry must not release the one-shot dispatch reservation. Stop further task input after the first terminal attempt, and keep the session identity for recovery even if cleanup fails. Keep these experimental records separate from employer-attempt/receipt records unless an explicitly reviewed mapping supplies equivalent evidence. Do not label task dispatch as one employer submission.

Before any experimental send, private packet readback must establish the exact saved values, document versions and bytes, employer/job URL, all required fields, prior-attempt state, and the scope of any origin access decision. Unknown prior outcomes still block retries. Only employer evidence may establish acceptance; a model statement, completed turn, trace span or deletion acknowledgement cannot. The risk of wrong-job, changed-payload or duplicate submissions inside a task remains even with every measure above. This is a limitation of the documented enforcement mechanisms, not a claim that the hosted browser cannot submit an application.

**Review outcome:** one scoped reduced-guarantee canary has private approval. Preserve the stronger invariant for normal production. The experimental adapter remains disabled and disconnected pending the technical and operational prerequisites below. New-company targets and exact private payloads also need their own approval, independent of this architecture decision.

## Disabled task-admission authority rehearsal

**Implemented offline, 2026-10-04:** `src/domain/hosted-task-admission-model.ts` models a separate experimental authority without importing a provider, repository, submit-seal RPC or receipt writer. Its mode is `OFFLINE_ONLY`. This is not a feature flag that enables candidate delivery.

The immutable binding contains the application, existing idle session, exact intended destination, packet digest, persisted admission key and hash of the exact serialized task message. The message hash identifies task admission only; it is never supplied as an employer request fingerprint. The state moves from RESERVED to ADMISSION_PENDING with `possibleEgress=true` **before** candidate-bearing task input or consequential origin approval. An acknowledgement moves to ADMITTED; stream loss, transport ambiguity, lease expiry or provider completion without employer evidence moves to UNCERTAIN. These states never expose FAILED_SAFE or automatic retry. A failure before possible execution closes the reservation as STOPPED rather than releasing it for an automatic retry.

The [session guide](https://developers.openai.com/api/docs/guides/agents-api/sessions) documents replaying admission after transport failure using the same `Idempotency-Key`, session and exact message. The model accepts only that identical replay and does not clear UNCERTAIN on a later acknowledgement. It refuses a new key, new session, changed message, duplicate task start or replay after a reconciled terminal outcome. This protects admission identity, not network actions inside the task.

`src/test-support/hosted-task-reservation-rehearsal.ts` is a **PGlite-only** persistence implementation with authority version `HOSTED_TASK_EXPERIMENT_V0_DISABLED`. It uses a private schema outside the migration directory; no SQL is applied to Supabase. A unique candidate/provider-job key excludes both modeled provider owners across different application rows and packet versions. A separate application key and session uniqueness constrain accidental reuse. Transactions lock the row and compare its version before storing immutable-binding transitions. The table has RLS enabled and no public privileges; this is not a reviewed production RPC/access policy.

The persistence tests close and reopen a filesystem-backed database, retain the admission key and possible-egress state, reject the modeled Browserbase owner after uncertainty and confirmation, reject packet replacement and stale writes, and exercise competing reservations and rollback. PGlite schedules these operations locally; this is constraint/transaction evidence, not a distributed load test. Model tests cover lost streams without an `application_attempt`, exact admission replay and externally verified employer-evidence reconciliation. The evidence input is a test seam, not a verifier or permission to mint a real receipt.

## Disabled native hosted adapter at checkpoint d8f7505

`src/server/workers/openai-hosted-canary.ts` now implements the actual session controller with an injected REST transport and durable-store interface. `openai-hosted-canary-transport.ts` implements documented REST calls and bounded SSE parsing. Neither is imported by production, and there is no live CLI or permissive default store. This is executable adapter code with synthetic tests, **not a completed production integration or a successful application**.

The controller creates an idle restricted-network desktop session with approved inline PDF files, subscribes to events before task admission, persists possible egress before candidate-bearing creation, and sends one task with a persisted admission key. Only an identical API-level admission replay is allowed after a lost acknowledgement. It retrieves pending origin actions and emits exact pre-recorded decisions. Missing origin permission, unsupported actions, malformed events, lost streams, budget refusal and cancellation stop the controller conservatively. Root turn completion does not establish acceptance. External evidence must match the application, destination and packet digest before the controller records an experimental confirmed outcome; the callback is not an implemented employer verifier or production receipt writer.

Cancellation uses a separate bounded request even after the run signal expires, then attempts deletion to stop the hosted environment. Normal terminal runs also attempt deletion. Session identity and the durable reservation remain retained; cleanup failure never permits a new task. If creating a session has an unknown result, the controller does not create a replacement. If the ID was received but saving it fails, it still attempts cancellation and deletion of that observed ID. An inaccessible unknown session or failed cleanup requires manual reconciliation, including spend; silence is not evidence of zero cost.

The store contract requires atomic approval and immutable-plan verification, existing-attempt checks, a durable candidate/job reservation shared across providers, controller fencing and a credible aggregate budget reservation. It deliberately supplies no production implementation. Synthetic in-memory adapter tests exercise sequencing and recovery; the separate PGlite rehearsal exercises persistence. They must not be represented as a completed shared production lock. Configured budget numbers and the three-minute controller deadline are **not a provider-enforced dollar ceiling**. Secure replacement credentials, current exact packet readback, authoritative prior-attempt checks, explicit origin decisions, and a defensible prior-plus-future spend bound are still required before any paid call.
